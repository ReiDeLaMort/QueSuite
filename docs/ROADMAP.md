# Baby-step roadmap

Broader operational capabilities are preserved in [OPERATIONS-REGISTER.md](OPERATIONS-REGISTER.md). They start as Captured / Not scheduled. Use pilot evidence to select the next increment; keep deferred or declined ideas with a reason so they remain discoverable.

The owner has also requested source-backed contributions by associates, visible credit, explained modifications/reversals, duplicate consolidation and sourcing-to-outcome traceability. [CONTRIBUTIONS.md](CONTRIBUTIONS.md) records this foundation. It applies to the next record-creation increment; authenticated membership is a prerequisite before independently operated multi-person attribution. A prototype may validate the workflow with its clearly labeled pilot actor, but personal credit must not be claimed from display names alone.

1. **Foundation 0.1 (complete):** PRD, domain boundaries, ADRs, OpenAPI contract, strict TypeScript, lint, repository tests, CI, persistent asset/work-order lifecycle.
2. **Locations and linked navigation 0.2 (implemented):** site → building → work area, asset location selection, record details, scoped references, and safe upgrade of existing records. Browser/device walkthrough, location editing, and legacy conversion remain future work.
3. **Manual meters and operational logs (proposed next):** both reading history and shift/maintenance notes, linked to assets and work orders. Validate units, provenance, corrections, and retries in the owner-led pilot. Automatic PM triggers remain later.
4. **One departmental handoff (proposed):** a shared request with QA, Maintenance, Accounting, Parts, and Logistics as participating departments; linked maintenance execution, explicit verification, and revisioned instructions/role guidance. Accounting can originate work or own a cost/documentation review task when required; it is not a universal approval gate. Use [SHARED-WORK.md](SHARED-WORK.md) for the working example. Agree the example, API contract, and additive schema before implementation.
5. **Identity, contribution and department access:** managed sign-in, company/department memberships, action permissions, active references and trustworthy individual attribution. Associates can create and contribute within scope; creation, review, reversal, merge and financial authority are separate permissions. Gate: cross-company, cross-department, attribution and permitted/denied action tests pass before separate people operate the workflow. Implement this dependency earlier if individual contribution features are selected before the departmental pilot.
6. **Offline proof:** installable app shell, IndexedDB cache/outbox, replay ordering, sync indicators, conflict review; extend the same rules to readings and notes. Gate: airplane mode, app restart, lost response, revocation, and concurrent-edit tests pass on target devices.
7. **Team field pilot:** limited equipment set, named users, observed departmental handoffs, feedback log, backup/restore rehearsal. Gate: the team verifies workflow effectiveness and no lost changes.
8. **One PM rule, then other modules:** connect a time/usage rule to the proven meter history and work-order flow; verify duplicate prevention and explicit acceptance. Preserve the requested parts catalog and equipment/location/department associations, Parts/Logistics fulfillment, and later supplier links/pricing/sourcing in OPS-005/006. Select the implementation order from actual feedback; none of these later items are yet scheduled.
9. **Multiple-company product:** tenant onboarding, operational monitoring, support, migration/restore practices, performance and isolation review. Billing follows demonstrated demand.

Current status: online owner-led prototype. Individual accounts, offline behavior, automatic scheduling, and production operations remain future work.

Domain registration, social handles, and public launch work are deferred at the owner's direction. They are not prerequisites for building or validating the app.
